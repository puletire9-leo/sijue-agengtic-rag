# 查询流程 v2：五层级联漏斗

> 当前实现状态与演进方向。✅ = 已实现，🔲 = 计划中。

---

## 一、五层级联漏斗模型

传统 RAG 是全量向量搜索。SuperMew v2 将检索拆为五层级联漏斗——便宜的层先过滤，只有少量候选进入昂贵的 LLM 层。

```
全部文档 (N)
  ↓ 查询规范化 ✅ 去口语词（"那个压缩的事"→"压缩"）
  ↓ 关键词路由 ✅ O(1) 倒排索引，零 LLM 消耗
候选文档 (≤15)
  ↓ 语义路由 ✅ 关键词未命中时向量搜摘要兜底
  ↓ (若语义也未命中 → 保留 top-15 做检索过滤) ✅
候选文档 (≤15)
  ↓ 文档路由 ✅ LLM 从候选中选 1~5 个文档
选中 1~5 文档
  ↓ 章节定位 ✅ 选中文档 ≤2 串行，>2 时 batch 合并为 1 次 LLM 调用
选中章节 + search_target
  ↓ 定向检索 ✅ 仅在选中章节下向量搜索 + 关键词跨文档关联
  ↓ (若定向 < 3 条 → 自动回退全局)
召回片段 → 重排 → 评估 → 生成
```

## 二、完整流程（实例推演）

**用户问**："那个多 Provider 的事怎么做的？"（口语化）

```
┌─ 护栏 & 快判 ─────────────────────────────────────────────┐
│ guardrail_query → fast_path → needs_retrieval = true       │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 记忆注入 ─────────────────────────────────────────────────┐
│ inject_memory: 会话/短期/长期三层记忆注入                    │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 检索策略决策 ─────────────────────────────────────────────┐
│ decide_retrieval: LLM 分析查询 → "entity_boosted"          │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 查询规范化 ✅ ────────────────────────────────────────────┐
│ _normalize_query: "那个多 Provider 的事怎么做的"             │
│   → 去口头禅: "多 Provider 的事怎么做的"                    │
│   → 用规范化查询做关键词路由，原查询兜底                      │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 智能路由（5 层漏斗）──────────────────────────────────────┐
│                                                            │
│ 第 1 层：关键词路由 ✅                                      │
│   "多Provider" 匹配 topics: "多Provider适配","Transport抽象"│
│   → 候选: 12 个文档                                        │
│                                                            │
│ 第 2 层：语义路由 ✅                                        │
│   关键词已命中 → 跳过。若关键词+规范化都未命中 → 向量搜摘要  │
│   若语义也未命中 → 保留 top-15 作为 route_fallback_docs ✅   │
│   （检索时用作文件名过滤，不浪费已有嵌入推理）                │
│                                                            │
│ 第 3 层：文档路由 ✅                                        │
│   LLM 从 12 个候选目录中自主选择:                           │
│   选中文档: ["01-多Provider适配.md"]（简单问题 1 个足矣）   │
│                                                            │
│ 第 4 层：章节定位 ✅（选中文档 >2 时 batch 合并）            │
│   选中仅 1 个文档 → 串行（1 次 LLM 调用）                   │
│   若选中 3 个文档 → batch 合并为 1 次调用 ✅                 │
│   选中: l1::0（架构总览）, l1::3（Transport 抽象层）        │
│   search_target: "ProviderTransport 抽象基类的四大方法..."   │
│                                                            │
│ 第 5 层：定向检索 ✅                                        │
│   filter: root_chunk_id in ["...l1::0", "...l1::3"]        │
│   向量搜索 → 召回 8 个片段                                  │
│   若 < 3 条 → 自动回退全局检索                               │
│                                                            │
│ 跨文档关联 ✅（当前：关键词交集）                            │
│   01-多Provider适配 topics ∩ 00-架构总纲 topics            │
│   → 追加 2 个相关片段 → 合计 10 个                          │
│   🔲 升级语义相似度关联                                     │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 查询改写 & 扩展 ──────────────────────────────────────────┐
│ rewrite_expand: 首次跳过，重试时启用 step_back/hyde/complex │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 渐进式重排 ───────────────────────────────────────────────┐
│ progressive_rerank: 归一化 → 加权融合 → 交叉编码 → 上下文   │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 文档评估 + 语义回退检查 ✅ ───────────────────────────────┐
│ grade_documents:                                           │
│   基本相关性: yes                                          │
│   search_target 检查:                                       │
│     预期: "ProviderTransport四大方法及职责..."              │
│     实际: 包含 Transport 方法描述 → YES                    │
│     (若预期未覆盖 → "no" → 触发 rewrite + 全局检索)        │
└────────────────────────────────────────────────────────────┘
  ↓
┌─ 生成 & 后处理 ────────────────────────────────────────────┐
│ compress_check → generate_answer → evaluate_confidence     │
│ → guardrail_output → post_process                          │
└────────────────────────────────────────────────────────────┘
```

## 四、关键决策

### 决策 1：关键词路由 vs 语义路由是 fallback 还是并集？

**当前选择**：fallback。关键词命中就跳过语义路由。候选 < `PREFILTER_MIN_CANDIDATES`（3 个）时走语义路由补充。

### 决策 2：口语规范化在哪一层做？

**当前**：关键词路由之前。先用规范化查询做关键词匹配，不成功再用原查询。规范化只用规则（去口头禅），不调 LLM。

**实测效果**：
- "那个压缩的事怎么做的" → "压缩怎么做的"（匹配"压缩"相关 topic）
- "帮我查一下多Provider适配" → "查多Provider适配"（匹配"多Provider"）
- "上下文压缩Pipeline" → 不变（无需规范化）

### 决策 3：Batch 章节定位的触发条件

**条件**：选中文档数 > `BATCH_CHAPTER_THRESHOLD`（2），且文档章节数 > 3。

选 1~2 个文档时串行更快（延迟 ≤ 2×LLM 延迟）。选 3~5 个文档时 batch 合并节省 2~4 次串行调用。Batch 失败时自动回退串行。

### 决策 4：search_target 粒度

prompt 里要求"信息类别，不要求精确数字"：
- ✅ "第三章财务数据部分关于2024年各季度营收的同比变化率"
- ❌ "第三章有营收12.7亿，同比增长3.2%"

### 决策 5：路由失败的兜底链

```
关键词路由失败 → 语义路由
  → 语义成功 → 文档路由 → 章节定位
  → 语义也失败 → route_fallback_docs = 语义 top-15
                → hybrid_retrieve 用 filename in [...] 做过滤
                → 过滤结果 < 3 → 完全放开全局检索
```

不浪费任何一次已有的嵌入推理。

## 五、成本分析

### 单次查询 LLM 调用（当前实现）

| 节点 | 模型 | 次数 | 触发条件 |
|------|------|------|---------|
| 查询规范化 | 无（规则） | 0 | 总是 |
| decide_retrieval | 轻量 | 1 | 总是 |
| 关键词路由 | 无 | 0 | 纯倒排 |
| 语义路由（嵌入）| 本地 BGE-M3 | 0~1 | 关键词未命中 |
| 文档路由 | 轻量 | 1 | 总是 |
| 章节定位 | 轻量 | 1（≤2 文档）或 1（batch） | 选中文档 > 0 |
| rewrite_expand | 标准 | 0~1 | 重试时 |
| progressive_rerank | API | 0~1 | 有远程 reranker |
| grade_documents | 标准 | 1 | 总是 |
| search_target 检查 | 标准 | 0~1 | 路由成功时 |
| generate_answer | 标准 | 1 | 总是 |
| evaluate_confidence | 轻量 | 1 | 总是 |

**典型查询**（关键词命中，选 2 文档，一次通过）：
- 轻量 LLM：4 次（decide + 文档路由 + 章节 ×1~2）
- 标准 LLM：2~3 次（grade + generate + 可能的 search_target）
- 嵌入：1 次（检索 query embedding）
- Token 总量：~5K~10K

**选 3+ 文档时的改善**（batch 章节定位）：
- 章节定位从 3~5 次 → 1 次
- 轻量 LLM 调用总数减少 2~4 次

### 成本结构

| 环节 | 占比 | 说明 |
|------|------|------|
| generate_answer | ~60% | 检索精准 → context 少 → 生成便宜 |
| 章节定位 | ~10% | Batch 后已降低 |
| grade_documents | ~10% | 二进制判断，考虑换轻量模型 |
| 其余 | ~20% | — |

## 六、已知缺陷与改进

### 缺陷 1：关键词路由对口语化查询无效 → ✅ 已修复
口语规范化后做关键词匹配，实测有效。

### 缺陷 2：路由失败丢弃中间结果 → ✅ 已修复
语义 top-15 保留为 `route_fallback_docs`，检索时做文件名过滤。

### 缺陷 3：章节定位串行延迟 → ✅ 已修复
选中文档 > 2 时 batch 合并为 1 次 LLM 调用。

### 缺陷 4：跨文档关联只看关键词交集 🔲
两个文档 topic 标签不同但语义相关时不会被关联。需要语义相似度关联。

### 缺陷 5：路由决策不可追溯 🔲
用户看不到"为什么选了 A 没选 B"。

### 缺陷 6：章节定位缺少上下文验证 🔲
LLM 可能将"多 Provider 适配"误定位到"多平台网关"的章节。

## 七、500+ 文档时的扩展路径

| 文档数 | 当前行为 | 问题 | 方案 |
|--------|---------|------|------|
| < 50 | 关键词→LLM 选 1~5 | 够用 | — |
| 50~200 | 同上 | 候选 15 中假阳性增多 | 动态缩小候选数 |
| 200~500 | 同上 | 语义路由精度下降 | 主题聚类预分组 |
| 500+ | 需要分级索引 | LLM 文档路由负担重 | 主题 → 文档 → 章节三级索引 |

## 八、与 Inspool query_wiki 的对比

| | Inspool query_wiki | SuperMew v2 |
|---|-------------------|------------|
| 索引层 | `wiki/index.md`（人工维护） | Topic 倒排 + 摘要向量（自动生成） |
| 定位方式 | 人读 index → 定位页面 | 规范化 → 关键词 → 语义 → LLM 四级路由 |
| 检索粒度 | 页面级（整篇 wiki）| 片段级（~300 字符）+ 父块回填 |
| 上下文扩展 | 手动双链 + frontmatter | 自动关键词关联 + 父块回填 |
| 矛盾处理 | 显式 contradicts 字段 | search_target 语义回退 |
| 维护成本 | 人 + Agent 持续维护 index | 上传全自动，检索全自动 |
| 可解释性 | 高（index 可读） | 低（路由决策不透明）🔲 |
